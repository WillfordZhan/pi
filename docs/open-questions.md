# 项目 Open Questions

本文记录 Pi Java Runtime 已知但尚未完全解决的架构边界、风险等级和升级触发条件。已经确认的当前方案单独列出，避免把既定决策与未决问题混在一起。

## 分级标准

| 等级 | 定义 | 处理要求 |
| --- | --- | --- |
| P0 | 已阻断当前核心流程，或可能造成上下文错误、越权、数据损坏 | 当前版本必须解决并留下回归测试 |
| P1 | 不阻断当前单实例文本会话，但会影响故障恢复、数据完整性或多实例部署 | 对应能力启用或扩大部署前解决 |
| P2 | 当前实现可用，主要影响长期兼容性、运维效率或扩展能力 | 触发条件出现后再设计，禁止提前扩建 |

## 已确认的会话恢复边界

```text
继续对话
  -> 优先打开 Pi 本地 JSONL
  -> 本地不存在时查询 Java Conversation Store
  -> 校验会话归属和 Entry 基本结构
  -> 修复历史同步 marker 缺失造成的父链断点
  -> 重建本地 Pi JSONL
  -> SessionManager.open()
  -> 继续执行 Pi 原生 agent loop
```

- Pi 本地 JSONL 仍是运行时真相源；Java Conversation Store 是管理查询和故障恢复镜像，不在每轮推理前替代 Pi SessionManager。
- 数据库恢复只在本地 JSONL 不存在时触发，正常续聊不增加 Java 查询。
- Java Entry 查询必须携带 `deptId` 和 `userId`，恢复后仍校验 JSONL 内的 `java_gateway_context`，会话 ID 不能单独作为访问凭证。
- 当前 Java 镜像不保存图片 Base64。恢复后的历史图片只保留文字占位，文本、工具调用、工具结果和压缩记录可继续参与上下文。
- 当前会话队列只保证单个 Pi Runtime 进程内串行；不把多实例并发控制混入本次恢复修复。
- 本次恢复复用 Pi 原生 JSONL 格式与 SessionManager，不新增第二套会话模型，也不修改 Java 接口或数据库结构。

## 待处理问题

### OQ-P0-001：数据库恢复时 Entry 父链不完整

- **等级**：P0
- **状态**：已解决
- **现象**：Runtime 本地找不到 JSONL 时直接返回 `Conversation not found`；即使直接重放数据库 Entry，第二轮开始也可能丢失更早上下文。
- **原因**：增量同步会把 `java_store_sync` marker 留在本地，但后续 Entry 的 `parentId` 会引用该 marker；Java 镜像过滤 marker 后形成断链。
- **实现结果**：本地缺失时从 Java 懒恢复；对历史缺失 marker 合成不参与模型上下文的兼容节点；后续同步携带新 Entry 所依赖的上一个 marker。
- **本地验证**：数据库缺失 marker 的两轮 Entry 经恢复后，`SessionManager.buildSessionContext()` 能读取完整两轮上下文；空 Entry 和非法 Entry 会在创建 JSONL 前失败。
- **Star2 验证**：本地 JSONL 不存在的历史会话可从 Java Entry 恢复并继续调用 Qwen；恢复后的 31 条本地 Entry 无父链断点，后续 Java 增量已保存同步 marker。
- **退出标准**：两轮及以上数据库 Entry 恢复后，`SessionManager.buildSessionContext()` 包含完整历史；本地已有 JSONL 时不调用 Java 恢复接口。

### OQ-P1-001：Java 同步失败时的恢复时间点

- **等级**：P1
- **状态**：开放
- **当前边界**：Pi 先落本地 JSONL，再尽力同步 Java；Java 同步失败不会把已经生成的模型回复改判为失败，下一轮会从最近 marker 重试。
- **风险**：如果 Java 同步失败后、本地 JSONL 重试成功前发生磁盘丢失，数据库恢复点会落后于用户已经看到的回复。
- **升级触发条件**：业务要求明确的零丢失恢复点，或实际出现本地会话卷丢失。
- **候选方向**：持久化重试队列或 outbox。未触发前不引入额外消息组件。

### OQ-P1-002：多 Pi 实例同时续聊同一会话

- **等级**：P1
- **状态**：开放
- **当前边界**：`conversationQueues` 只在单个 Node.js 进程内按会话串行，单实例部署可用。
- **风险**：多副本收到同一会话的并发请求时，可能各自从相同叶子创建分支，并以不同顺序同步 Java。
- **升级触发条件**：Pi Runtime 扩为多副本，且无法保证同一 conversationId 粘性路由到同一实例。
- **候选方向**：优先使用网关一致性路由；确有跨实例并发需求时再增加带租约的分布式会话锁。

### OQ-P1-003：历史图片的完整恢复

- **等级**：P1
- **状态**：开放
- **当前边界**：Java 镜像只保存图片数量占位，不保存 Base64；数据库恢复后的模型无法重新读取历史图片内容。
- **风险**：用户追问“上一张图片”时，模型只能知道曾经存在图片，不能重新分析原图。
- **升级触发条件**：产品明确要求跨机器、跨容器或本地卷丢失后仍能继续引用历史图片。
- **候选方向**：将图片保存到 OSS，只在 Pi Entry 和 Java 镜像中保存受控对象引用；禁止重新把大段 Base64 写入会话查询表。

### OQ-P2-001：Pi SessionEntry 版本演进

- **等级**：P2
- **状态**：开放
- **当前边界**：数据库保存当前 Pi 原始 Entry；恢复时生成当前版本 Session Header，并由 SessionManager 读取。
- **风险**：未来 Pi 修改 Entry 结构后，旧数据库 Entry 可能需要显式迁移，不能只更新 Header 版本掩盖结构差异。
- **升级触发条件**：升级 Pi 时出现 Session 格式版本变化，或 SessionManager 新增 Entry 迁移要求。
- **候选方向**：在升级验收中加入历史数据库 Entry 恢复样本；只有真实版本差异出现时才增加迁移器。
